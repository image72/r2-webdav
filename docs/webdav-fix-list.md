> **B4/B5/B8 的设计取舍（需要你确认的一个行为变化）**
> PROPPATCH 从"假装成功"改成**如实回 403**：RFC 4918 §9.2 要求服务器不设置的属性必须
> 逐个回 403，且整个请求必须原子地失败。不实现"死属性"是刻意决定：
> R2 binding **没有"只改元数据"的接口**，要存属性必须把整个对象重传一遍（自定义元数据
> 还有 2 KiB 上限），而 Finder / Windows 每次上传都会发 PROPPATCH —— 代价与收益完全
> 不成比例。改动同时去掉了那次无意义的重传（B8）。
> 风险：若某个客户端把 PROPPATCH 失败当上传失败，可用一行改回"接受并忽略"
> （把 `403 Forbidden` 换成 `200 OK`）。**建议你在 Finder 里实测一次上传。**

> **C12 的结论：不实现配额，而不是编造数值。** 计算已用空间需要遍历整个 bucket
> （子请求爆炸），而 RFC 4331 规定服务器不支持配额时**不应**返回这两个属性 ——
> 返回 0 反而会让客户端以为磁盘已满。现在显式请求它们会得到 `404 propstat`（Batch 4
> 的收敛逻辑顺带实现了这一点），`allprop` 里也不会出现。

> **B10 的迁移影响**：现在 `make_resource_path()` 会解码（`decode_path`），href 会重新编码
> （`encode_path`），两者互逆。存量对象仍然可达 —— 旧版本把 `old name.txt` 存成了 key
> `old%20name.txt`，新版本会输出 `/old%2520name.txt`，客户端请求回来解码后正好命中旧 key
> （已实测）。唯一的代价：这类**存量**对象在各客户端里显示的名字会变成 `old%20name.txt`
> （以前显示 `old name.txt`）；新写入的文件名从此是正确的。
> 另外 `Destination` 头、网页界面的 `directory_path()` 也必须同步解码，否则 COPY/MOVE
> 的目标名会写成编码形式（第一次就漏了 Destination，被回归抓到）。

> **A3/A4 的残余限制（平台相关）**：修掉的是"静默"，不是"上限"。单次请求仍然最多枚举
> `MAX_OBJECTS_PER_REQUEST`(3000) 个成员；现在超限会明确失败（COPY/MOVE → `507`，
> PROPFIND → `<responsedescription>` + `X-WebDAV-Truncated: true`，网页界面 → 顶部警示条），
> 而不是假装成功。真正的分页需要 WebDAV 之外的游标机制，见下方平台受限表。

> **B3 的修法**：没有让 PUT 层层补建祖先目录（那会给每次深层 PUT 增加多次子请求），
> 而是新增 `listDir()` 读取 R2 的 `delimitedPrefixes` —— 隐式目录在任意列表里都能出现，
> 且 `resource_exists()` 让 PROPFIND / DELETE 也能识别它们。存量幻影目录因此一并被救活。

> **A6 说明**：本地观察到的 `500` 是 Miniflare 的 R2 条件读取实现缺陷（错误页内容为
> `Error get: Unspecified error (0)`），生产 R2 未必复现。但代码层面确实存在两处真实缺陷且已修：
> ① 条件不满足时一律回 `412`，而 RFC 9110 要求 GET/HEAD 的 `If-None-Match` /
> `If-Modified-Since` 回 `304`；② 条件判断完全委托给 R2 的 `onlyIf`，无法区分这两种结果。
> 现在改为 `evaluate_conditionals()` 自行按 §13.2.2 的优先级求值（1 次请求，无额外子请求）。

> **C2/C1 附带教训**：不能用 `object.range !== undefined` 判断"是否返回了片段" ——
> R2 在请求**没有** Range 头时也会返回覆盖整个对象的 range，那样会让所有普通下载都变成
> `206 + Content-Range`（我第一版就这么写错了，被回归抓到）。必须用长度比对。

## F. 网页界面（修复过程中新发现）

| ID  | 问题                                                                                                                                                           | 证据                                                 | 状态   |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------ |
| F1  | 拖拽/选择上传同名文件时**静默覆盖**（无提示、无确认），只在事后弹一句“已上传 N 个文件”                                                                         | [实测] 内容 `ORIGINAL-CONTENT` → `REPLACED`          | 已修复 |
| F2  | “新建文本文件”默认名恒为 `untitled.txt`：只要该名已存在，新建流程一打开就处于重名风险中，连点两次保存即覆盖原有文件                                            | [实测] 默认名 `untitled.txt`                         | 已修复 |
| F3  | **P0**：编辑器的 `conflict` 标记一旦置位就永不重置 —— 改名到**另一个**已存在的文件后首次保存会**直接覆盖**它（警告文字还是上一个文件名留下的，看起来像已确认） | [实测] `second.txt`：`ORIGINAL-SECOND` → `CONTENT-A` | 已修复 |

> **F3 为什么是 P0**：它不是“提示不到位”，而是**探测被彻底跳过**。
> 旧逻辑 `if (!editor.href && !editor.conflict)` —— 第一次撞名后 `conflict = true`，
> 之后无论改成什么名字都不再发 `HEAD` 探测，直接 `PUT`。
> 修法是让 `conflict` 跟随文件名复位（输入框上 `@input="editor.conflict = false"`），
> 于是“再点一次保存就覆盖”这句话**只对当前这个名字成立**，无法通过改名绕过。
>
> **F2 的修法**：新建时用 `default_new_name()` 在已加载的 `entries` 里挑一个不冲突的名字
> （`untitled.txt` → `untitled-2.txt` → …），**不发额外请求**；同时 `untitled.txt` 已存在
> 这件事不再把用户直接推到“重名 - 再点一次 - 覆盖”的边上。
>
> **F1 的修法**：上传时发 `If-None-Match: *`，`412` 不当作失败而是收集起来，全部传完后再弹
> 一张确认表（列出文件名，超过 5 个折叠为“……以及另外 N 个”），确认后才重跑一遍覆盖。
> 同名**目录**单独识别（缓存条目 + 一次带 `<collection />` 的 PROPFIND 交叉校验，防列表过期），
> 归入“跳过同名目录”而不是覆盖。

## 平台受限项（记录后跳过）

这些**无法在 Cloudflare Workers 上按要求完成**，不在本轮修复范围内，仅记录原因与替代方案：

| 项                                            | 平台原因                                                                                                                     | 替代方案                                                                                                                                                                   |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B6 真锁**（互斥锁、423 Locked、token 校验） | Workers 是无跨请求共享状态的隔离运行环境；锁必须持久化到共享存储才有效。真正的锁需要 **Durable Objects**（或 KV + 竞态处理） | 保留 advisory stub（Office/Windows 需要 LOCK 存在才能工作），把便宜的一致性细节修对，并**在文档中明确"锁不具强制力"**。彻底实现需引入 DO 绑定，属独立的架构变更            |
| **B8 只改元数据的更新**                       | R2 Workers binding **没有** updateMetadata / copy-with-replace 接口：要改 `customMetadata` 就必须重新 `put` 整个对象         | 已改为"零写入 + 如实回 403"（不再做那次重传）。若将来要支持死属性，需要旁路对象（sidecar）或 DO                                                                            |
| **E3 大文件上传 / 分块续传**                  | Cloudflare 请求体上限 100 MB（Free/Pro）/ 200 MB（Business），且 Worker 无法绕过；WebDAV 本身没有标准的分片上传              | 已修 B7：对 `Content-Range` 明确回 `501`，**不再静默产出截断文件**；大文件需走 S3 兼容 API（`createMultipartUpload`）而非 WebDAV                                           |
| **A4 列表分页**                               | 单次响应可枚举的成员数受 CPU（Free 仅 10 ms）与子请求配额限制；WebDAV 没有标准的分页游标，Worker 内也无法跨请求保存遍历状态  | 已改为**显式失败**而非静默截断（COPY/MOVE → 507；PROPFIND → `<responsedescription>` + `X-WebDAV-Truncated`；网页界面 → 警示条）。彻底方案需 Queues / DO 承载可续的任务状态 |
| **D1 子请求上限下的"一次性"COPY/MOVE**        | Free 1,000 / Paid 10,000 子请求，超出即终止（COPY 每成员 2 次 R2 调用、MOVE 3 次）                                           | 已改为"有界 + 明确失败"（507），不再静默丢数据。彻底方案同上                                                                                                               |
| **D3 PROPFIND 的 CPU 开销**                   | 平台 CPU 配额；代码只能在预算内减少工作量                                                                                    | 现在支持按请求体收敛属性（`<prop>` / `<propname/>`），客户端可以只要它需要的字段；Paid 计划可调 `limits.cpu_ms`                                                            |
| **D2 6 连接并发**                             | 平台每次调用最多 6 个等待响应头的连接                                                                                        | 已把常量从 50 改成 6，并注明原因，避免"50 路并发"的错觉                                                                                                                    |
